# Chat History Persistence — Backend Spec (Hand-off)

> **Audience:** the engineer who owns the BloomBrain FastAPI repo on the data VPS.
> **Status:** frontend is ready; only the backend pieces below are missing.
> All endpoints below should be mounted at `/chat/...` under the existing
> BloomAI API, behind the same JWT auth the rest of the chat surface uses.

## 1. Why we need this

Today the frontend persists chat history **only in the user's browser
`localStorage`** under keys `messages_<sessionId>`. The backend tracks the
*existence* of each session (`chat_sessions`) and the per-hop **cost** of every
LLM call (`cost_events`), but it does **not** store the actual message text.
Symptoms users hit because of this:

- Switching browsers / devices loses every assistant reply.
- Clearing site data loses every assistant reply.
- Navigating to a different chat (or refreshing) mid-stream loses whatever
hadn't yet finished streaming.
- Quota errors on the 5 MB `localStorage` cap silently drop saves.

We've already shipped two frontend mitigations (incremental save during
streaming, and an "history isn't on this device" empty-state). This spec
covers the **only real fix**: persist message text server-side and expose it.

## 2. Data model

Add one new table. We **don't** want to overload `cost_events` for this — that
table is keyed per-hop (one row per LLM call) and we'd be duplicating the
turn-level user text on every retry. Keep cost data and message text separate.

```sql
CREATE TABLE chat_messages (
  id                  UUID         PRIMARY KEY DEFAULT gen_random_uuid(),
  session_id          UUID         NOT NULL REFERENCES chat_sessions(id) ON DELETE CASCADE,
  user_id             UUID         NOT NULL REFERENCES users(id),
  role                TEXT         NOT NULL CHECK (role IN ('user', 'assistant', 'system', 'tool')),
  content             TEXT         NOT NULL,
  -- Matches `cost_events.turn_id` so a message can be cross-referenced
  -- with its cost rows. Generated by the chat endpoint per logical user turn.
  turn_id             UUID         NOT NULL,
  -- Optional client-supplied dedupe id (matches what the frontend already
  -- sends via the existing `client_message_id` field in SendMessageRequest).
  client_message_id   TEXT,
  -- Snapshots of the most recent rendering metadata. Optional; lets us show
  -- model/cost badges on historical messages without an extra cost-events join.
  model               TEXT,
  mode                TEXT,          -- 'thinking' | 'balanced' | NULL
  input_tokens        INT,
  output_tokens       INT,
  cached_input_tokens INT,
  total_cost          NUMERIC(12,6),
  latency_ms          INT,
  error_kind          TEXT,
  -- attachments are already in their own table keyed by client_message_id;
  -- no need to denormalise here.
  created_at          TIMESTAMPTZ  NOT NULL DEFAULT now()
);it

CREATE INDEX chat_messages_session_created_idx
  ON chat_messages (session_id, created_at);
CREATE INDEX chat_messages_user_idx
  ON chat_messages (user_id);
CREATE UNIQUE INDEX chat_messages_client_id_idx
  ON chat_messages (session_id, client_message_id)
  WHERE client_message_id IS NOT NULL;
```

**Retention:** keep messages as long as `cost_events` (currently indefinite).
If you ever add a TTL, prune both tables together.

## 3. Where to write rows

The existing chat endpoint `POST /chat/sessions/{session_id}/messages`
already streams the assistant reply back to the browser. Hook the writes in
the same place that currently records `cost_events`:

1. **As soon as the user message is received** (before any LLM call):
  write one row with `role='user'`, `content=request.content`,
   `client_message_id=request.client_message_id`, `turn_id=<new>`.
2. **At the end of each LLM hop** (where `cost_events` is currently appended):
  write one row with `role='assistant'`, `content=<final assistant text for  this hop>`, plus the same `turn_id` so it groups with the cost rows.
   For multi-hop turns (tool use, fallbacks) emit one assistant row per hop
   the same way `cost_events` does.
3. **On stream disconnect** (browser closed mid-stream): persist whatever was
  already generated. The existing cost recorder already handles this — same
   place, just also write the assistant text.
4. **On error** (provider 5xx, content filter, etc.): write one row with
  `role='assistant'`, `content=''` (or the partial text we generated),
   `error_kind=<reason>`. This matches how `cost_events.error_kind` is
   recorded today.

Slack-recorded turns (via `POST /cost/ingest`) should **also** persist
messages. Extend the ingest payload to include `user_content` and
`assistant_content` and write them to `chat_messages` the same way. (Sessions
for Slack: we don't currently mint `chat_sessions` rows for Slack DMs — if
that's still true, either auto-create one per `slack_thread_ts` or skip Slack
messages for now and only persist web-chat history. Your call.)

## 4. New endpoint

```
GET /chat/sessions/{session_id}/messages
```


| Param        | In    | Type         | Description                                                                              |
| ------------ | ----- | ------------ | ---------------------------------------------------------------------------------------- |
| `session_id` | path  | UUID         | Required. The session to load.                                                           |
| `limit`      | query | int          | Optional, default `200`, max `500`. Most-recent-first when paginating with `before`.     |
| `before`     | query | ISO datetime | Optional. Return only messages with `created_at < before`. Used for "load older" scroll. |
| `after`      | query | ISO datetime | Optional. Used for resyncing after an offline period.                                    |


**Auth:** standard JWT bearer (same as everything else under `/chat/`*).
**Scoping:** must enforce `chat_messages.user_id == jwt.user_id`. Return 404
(not 403) if the session belongs to another user, to avoid leaking session
existence. Admins (`users.is_admin = true`) may pass `?user_id=<uuid>` to read
another user's history, mirroring the existing `/cost/users/{id}/summary`
pattern.

**Response:** `MessageRow[]`, ordered by `(created_at ASC, turn_id ASC, hop_index ASC)`
so the frontend can append directly without re-sorting. Include attachments
inline (we already have an `/attachments` endpoint, but inlining one round
trip on initial load is cheap and matches the localStorage shape the frontend
already speaks).

```ts
interface MessageRow {
  id: string;              // UUID
  session_id: string;
  role: 'user' | 'assistant' | 'system' | 'tool';
  content: string;
  turn_id: string;
  hop_index: number | null;   // for assistant rows of multi-hop turns
  client_message_id: string | null;
  model: string | null;
  mode: 'thinking' | 'balanced' | null;
  input_tokens: number | null;
  output_tokens: number | null;
  cached_input_tokens: number | null;
  total_cost: number | null;     // USD
  latency_ms: number | null;
  error_kind: string | null;
  attachments: AttachmentRow[];  // same shape as /chat/sessions/{id}/attachments
  created_at: string;            // ISO datetime
}
```

**Status codes:**

- `200` with `[]` if the session exists but has no messages yet.
- `404` if the session doesn't exist or isn't accessible by the caller.
- `401` if the JWT is missing / expired (consistent with the rest of the API).

## 5. Backfill (optional but recommended)

Sessions created before this lands have no rows in `chat_messages`. Two
options:

1. **Do nothing.** New chats persist, old ones stay localStorage-only. The
  frontend already shows a friendly "history not on this device" card when a
   session returns `[]`, so this is acceptable.
2. **Best-effort backfill from cost_events.** Each `cost_events` row already
  has a `turn_id` and per-hop metadata, but **does not** contain message
   text — so we can only backfill *skeletons*. Not worth the effort; just go
   with option 1.

## 6. Frontend contract (already in place)

The frontend is wired and only waiting for this endpoint to exist. When it
ships, the change on our side is small and lives in `chat-area.jsx`:

```js
// On session load:
APIService.getSessionMessages(conversationId)
  .then((server) => {
    if (server?.length) {
      setMessages(normalise(server))
      saveMessages(conversationId, server)   // keep localStorage as a warm cache
      setHistoryMissing(false)
    } else {
      const local = loadMessages(conversationId)
      setMessages(local)
      setHistoryMissing(local.length === 0)
    }
  })
  .catch(() => {
    // Network/API failure → fall back to localStorage so the chat still works offline
    const local = loadMessages(conversationId)
    setMessages(local)
    setHistoryMissing(local.length === 0)
  })
```

No other frontend changes are required.

## 7. Acceptance criteria

A change is "done" when **all** of the following hold:

1. `GET /chat/sessions/{id}/messages` returns the full conversation, in order,
  including multi-hop assistant turns, for both web and (if implemented)
   Slack-originated chats.
2. Killing the streaming connection mid-reply (`SIGINT` the curl, close the
  tab, kill nginx between Tomcat and client) still results in a partial
   assistant row being persisted, just like cost rows are persisted today.
3. A user logging in from a clean browser sees their full history (titles +
  messages) without touching localStorage.
4. A different user calling `/chat/sessions/{otherId}/messages` gets `404`,
  not `200` with someone else's data.
5. The endpoint paginates correctly with `limit` + `before` (no N+1 from the
  attachments inlining; one round trip per page).

## 8. Where to ping if something breaks

- If `chat_messages` writes silently stop, search backend logs for
`record_chat_message failed` (mirror the existing `record_chat_cost failed`
pattern).
- If the endpoint is returning `[]` for sessions that clearly have rows in
the DB, check the user-scoping clause first — leakage protection is easy
to over-tighten.
- If Slack DMs are missing history but web chats are fine, check whether the
`/cost/ingest` extension was deployed alongside the main API change.
